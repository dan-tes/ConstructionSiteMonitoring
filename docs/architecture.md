# Архитектура

## Компоненты

```
frontend (React) ──HTTP──▶ backend (FastAPI) ──▶ PostgreSQL
                               │   ▲
                   *.command   │   │  *.result
                               ▼   │
                     RabbitMQ, exchange csm.analysis
                               │
        ┌──────────┬───────────┼──────────────┬──────────┐
     planner     vision   visual_phase      phase      delay
```

Backend работает как оркестратор: он решает, какой шаг запускать следующим.
Сервисы друг с другом не общаются и backend напрямую не вызывают. Все
межсервисные вызовы, включая быстрые, идут только через RabbitMQ. Прямых
HTTP-вызовов между backend и сервисами нет.

| Сервис | Что делает |
| --- | --- |
| **planner** | Разбирает план в свободной форме с помощью YandexGPT. Каждая строка относится к одной из 43 канонических работ, затем работы собираются в 10 фаз |
| **vision** | YOLO (обучен на MOCS) находит технику и людей на видео и фото и считает их по классам |
| **visual_phase** | Определяет фазу прямо по кадру. Это ансамбль из головы над DINOv2, головы над SigLIP и zero-shot SigLIP. На видео усредняются 6 кадров |
| **phase** | Определяет текущую фазу проекта. Объединяет модель по технике и визуальные вероятности скрытой марковской цепью по порядку фаз (`services/phase/fusion.py`) |
| **delay** | Прогнозирует отставание от графика по методу Earned Schedule |

Фазы строительства по порядку: Preconstruction, Site Preparation, Earthwork,
Foundation, Structural Frame, Masonry, MEP, Finishing, External Works,
Commissioning.

## Путь записи журнала

1. Пользователь загружает запись: дату, автора, комментарий и до нескольких
   видео или фото.
2. Backend отправляет `vision.command` на каждый файл и один
   `visual_phase.command` на всю запись.
3. Когда пришли все `vision.result` и `visual_phase.result`, backend
   отправляет один `phase.command` на запись. Если визуальный сервис не
   ответил за 600 с, backend не ждёт дальше. В команду входит визуальная
   история проекта.
4. После `phase.result` backend отправляет `delay.command`.
5. Когда приходит `delay.result`, запись получает статус `ready`. Если
   задан ключ YandexGPT, `backend/report.py` генерирует текстовые отчёты:
   по записи и по проекту в целом.

Статус записи проходит путь `pending` → `analyzing` → `ready` / `failed`.
Frontend опрашивает API, пока анализ идёт. Если backend перезапустился
посреди анализа, незавершённые анализы ставятся в очередь заново.

## План проекта

План загружается файлом `.xlsx`, `.xls` или `.csv`. Разбор идёт одним из
двух путей, и оба пишут результат в таблицу `plan_stages`:

- **Быстрый путь** (`backend/plan_parser.py`). Файл `.xlsx` уже в
  каноническом формате: 21 фиксированная колонка, одна строка на работу.
  Разбирается синхронно, прямо в запросе загрузки.
- **Через LLM** (сервис `planner`). Всё остальное разбирается асинхронно.
  Frontend опрашивает статус так же, как у видео.

В каноническом плане нет календарных дат, только длительности. Поэтому
датой начала проекта считается дата самой ранней записи в журнале.

После закрытия проекта (`POST /projects/{id}/close`) отчёт «план — факт»
сохраняется в `.xlsx`, и проект больше не принимает изменений.
