# Модуль 1. План объекта (planner)

Код: `backend/plan_parser.py` (быстрый путь), `services/planner/` (разбор через LLM).

## Зачем

Фазу и отставание можно оценить только относительно плана: какие фазы есть
в проекте, в каком порядке они идут и сколько длятся. Заказчики присылают
планы в своём формате: выгрузки из MS Project или Primavera, Excel с
собственными названиями колонок и работ. Модуль приводит любой такой план к
10 каноническим фазам.

## Как работает

**Быстрый путь.** Если загружен `.xlsx` в каноническом формате (21
фиксированная колонка, одна строка на работу), `plan_parser.py` разбирает
его синхронно, прямо в запросе загрузки. LLM здесь не участвует. Разбор
строгий: без нечёткого сопоставления колонок и ровно один `project_id` на
книгу.

**Через LLM.** Всё остальное (`.csv`, `.xls`, `.xlsx` другой формы) уходит
в сервис `planner` и обрабатывается асинхронно. `plan_normalizer.py` делит
работу между LLM и обычным кодом:

1. LLM (YandexGPT) определяет, какая колонка исходной таблицы что содержит:
   название, длительность, даты, уровень вложенности.
2. LLM относит каждую строку к одной из 43 канонических работ. Это закрытый
   словарь из `data/canonical_plan.xlsx` вида «работа → фаза → ожидаемая
   техника». Строки обрабатываются пачками по 25.
3. Единицы измерения, длительности, валидацию и сборку по фазам делает
   обычный код, без LLM.
4. Общую длительность проекта по критическому пути одним узким запросом
   оценивает LLM, потому что графа зависимостей в свободном плане нет.

Ответ модели считается недоверенными данными. Если название вне словаря,
строку переспрашивают. Если ответ не удаётся разобрать, весь результат
получает статус `failed`, и угаданное значение дальше не передаётся:
неверная фаза или длительность испортили бы прогноз отставания. Строки с
уверенностью ниже 0.75 помечаются для проверки экспертом. Лог нормализации
объясняет, что случилось с каждой строкой.

Результат обоих путей записывается в одну таблицу `plan_stages`.

## Качество

Количественной оценки нет: набора планов с эталонной разметкой по работам
пока не собрано. Автотесты backend покрывают оба пути: канонический файл
проходит без LLM, а ошибка LLM помечает план как `failed`. Качество
классификации можно проверить по логу нормализации и по числу строк,
отправленных эксперту.

## Ограничения

- В каноническом плане нет календарных дат. Дата начала проекта берётся из
  самой ранней записи журнала.
- Длительность по критическому пути в пути через LLM — это оценка модели, а
  не расчёт.
- Для работы нужен ключ Yandex Cloud: без него сервис не запускается.
